## 导读

生成一段文字或图片，只需要判断最后的结果是否可用。让 AI 修改代码、管理计算集群或参与数学证明时，问题会复杂得多：系统不仅要给出结果，还要能说明用了哪些模型、执行了哪些步骤、花费多少资源，以及怎样确认结果没有越过边界。

9 月 5 日值得关注的进展，正好覆盖这条从生成到验证的路径。Anthropic 公布了由 Claude 参与完成的费马大定理形式化工程；GitHub 让多个模型在一次编程任务中分工；AWS 把基础设施规则封装为智能体可以调用的受限操作。Google 与 Microsoft 扩大音乐、图像模型的开发者入口，Extropic 则尝试让模型结构适应一种不同于 GPU 的概率计算芯片。

本期报道范围为北京时间 2026 年 9 月 5 日 00:00—24:00。公告按页面时间戳、官方订阅记录或可核验的发布时间换算归日；正文时间均按北京时间表述。“发生了什么”整理来源披露的事实，“为什么重要”和“值得关注”是编辑分析。厂商自报的性能与效率数字不视为独立评测结果。

## 今日要点

- Anthropic 公开费马大定理的完整 Lean 形式化成果和代码，称 Claude 智能体在 11 天内完成主要工作；成果验证的是既有数学证明，不是发现新的费马大定理证明。
- GitHub 发布 HydraFusion 研究预览，根据任务选择单模型、逐级升级或跨模型评审三种编程流程。
- Microsoft 将 MAI-Image-2.6 与更快的 Flash 版本带入 Foundry 公共预览，支持多图参考编辑、网页信息辅助和动态宽高比。
- Google 向 Gemini 应用和 Gemini API 推出 Lyria 3.5，可根据文字或图片生成带人声与结构的较长音乐。
- AWS 公开 HyperPod InstantStart，把集群创建、训练和部署操作封装成网页界面、REST 接口与 38 个受限工具。
- Extropic 发布面向 Z1 概率芯片的稀疏类 Transformer 实验，同时开放一个模型权重和训练方案；目前效率数字主要来自小模型和理论估算。

## 重点进展

### Claude 完成费马大定理形式化，机器检查究竟确认了什么？

**发生了什么**

Anthropic 公布费马大定理的端到端 Lean 形式化成果。Lean 是一种证明助手：人或程序把数学命题写成严格的形式语言，再由一个较小的检查核心逐步验证推导是否合法。Anthropic 称，多个 Claude 智能体借助 Prove2Me 协作平台，在 11 天内生成约 1,300 万行 Lean 代码，最终证明使用约 29,500 个中间定理，并消耗约 60 亿个输出词元。[来源：Anthropic 研究说明](https://www.anthropic.com/research/formalizing-fermats-last-theorem)

公开仓库把最终命题与 Mathlib 中的费马大定理陈述进行比较，并限制证明只能依赖 Lean 的三个标准公理。仓库记录称，全部 60,475 个模块通过 Lean 核心检查，另有 Comparator 和用 Rust 编写的 nanoda 核心进行复核；完整重建需要约 67 GB 磁盘，Anthropic 的 96 并行任务构建耗时 5 小时 32 分钟，峰值内存 153 GB。[来源：形式化成果仓库与复核说明](https://github.com/anthropics/fermats-last-theorem)

这项工作形式化的是 Wiles、Taylor-Wiles 等人已有证明路线，而不是让 Claude 重新发现一个未知的费马大定理证明。仓库也明确把它称为不维护、不接受贡献的研究产物，并提醒自动检查只能确认形式命题的推导，不能保证每个中间定理的名称或自然语言解释都准确。

**为什么重要**

形式化验证给 AI 参与数学研究提供了一条比“另一个模型觉得答案正确”更坚实的检查路径。即使生成过程规模巨大、人工难以逐行阅读，小型证明核心仍能判断最终命题是否从允许的公理推出。

但机器通过不等于成果已经容易理解、容易维护或得到独立复现。公开代码让外部团队能够检查，庞大的硬件和构建成本又提高了复核门槛。下一步应关注独立团队能否重建结果，以及是否能把高度重复的机器产物整理成数学家能够阅读和继续扩展的结构。

### HydraFusion 为什么不再要求开发者先选定一个模型？

**发生了什么**

北京时间 9 月 5 日 00:04，GitHub 发布 Project HydraFusion 研究预览。用户在 Copilot 命令行工具中选择一次 HydraFusion，运行时再按任务决定三种路径：由一个模型直接完成；先让较便宜的模型尝试，不达标时升级；或让另一模型家族在只读环境中评审初稿，再由原模型修订。[来源：GitHub HydraFusion 公告](https://github.blog/ai-and-ml/github-copilot/project-hydrafusion-frontier-quality-via-multi-model-orchestration/)

预览面向所有 GitHub Copilot 套餐，通过实验功能开启，费用按实际调用模型的词元分别计算。GitHub 还说明，每个步骤都有超时和取消规则，评审模型不能修改仓库，流程失败或没有通过验证时不会应用补丁；运行记录会汇总每一步的角色、结果、成本和延迟。

GitHub 在三项离线编程评测中，把经过调优的 HydraFusion 与 Claude Opus 5 比较。公司报告，TerminalBench 2.1 的正确率高 4.9 个百分点、估算成本低 67%；DeepSWE 和内部 CheckpointBench 的正确率分别低 1.5 和 0.1 个百分点，估算成本低 36% 和 65%。这些是 GitHub 在固定模型池和价格假设下得到的内部结果，预览阶段尚不能证明真实项目也有同样收益。

**为什么重要**

模型选择正在从用户开始任务前的一次决定，变成运行过程中可以调整的步骤。简单任务只调用一次模型，困难任务才增加评审或升级，有机会在质量、延迟和成本之间取得更细的平衡。

多模型也会带来新的可观察性问题。开发者需要知道一次结果实际调用了谁、触发了几次升级、总成本怎样计算，以及评审是否真正独立。HydraFusion 把这些问题写进运行时规则，比只宣传“多个模型合作”更接近可审计的工程方案。

### 两个图像模型怎样区分高质量与高吞吐任务？

**发生了什么**

北京时间 9 月 5 日 00:02，Microsoft AI 宣布在 Microsoft Foundry 公共预览 MAI-Image-2.6 和 MAI-Image-2.6-Flash。前者侧重精细生成与编辑，后者面向低延迟和高吞吐；两者都支持多张参考图编辑、利用网页信息补充画面内容、动态宽高比和最高 1.5K 分辨率。[来源：Microsoft AI 发布说明](https://microsoft.ai/news/pushing-the-quality-cost-frontier-with-mai-image-2-6/)、[模型页](https://microsoft.ai/models/mai-image-2-6/)

Microsoft 称 Flash 版本生成速度比 GPT-Image-2-Medium 快 2.8 倍，并给出 72% 的效率提升；公司还引用 Arena 和 Artificial Analysis 的榜单位置说明 2.6 的质量。这些比较来自厂商选择的测试条件与外部榜单快照，公告没有提供覆盖不同尺寸、编辑类型和并发量的完整延迟分布。

**为什么重要**

生产系统很少只追求最高单张质量。交互式编辑、批量商品图和最终广告成片，对延迟、成本与精度的要求不同。把同一家族拆成精细版与快速版，让团队能够按任务路由，而不是把所有请求都送进最昂贵的配置。

不过，带网页信息辅助的图像生成也扩大了核验范围。画面是否准确、引用的信息是否过时、编辑是否保留人物或产品身份，仍需要应用层检查；榜单名次不能替代具体业务素材上的测试。

### Lyria 3.5 怎样把音乐生成带进普通应用和 API？

**发生了什么**

北京时间 9 月 5 日 00:00，Google 发布 Lyria 3.5，并把它加入 Gemini 网页与移动应用、Gemini API、Google AI Studio、Flow Music 和 Google Vids。应用用户可以选择人声或纯音乐、使用模板，并指定较短或较长的曲目；开发者通过模型标识 `lyria-3.5` 调用。[来源：Google 发布公告](https://blog.google/innovation-and-ai/products/gemini-app/better-tracks-lyria-gemini/)、[Gemini API 音乐生成文档](https://ai.google.dev/gemini-api/docs/music-generation)

开发文档显示，Lyria 3.5 可以接收文字或图片输入，输出 44.1 kHz 立体声 MP3，并按提示组织主歌、副歌和桥段，时长可控制到数分钟。Google 的模型页称曲目最长可到 3 分钟，并说明所有生成或编辑的音乐都会加入不可感知的 SynthID 水印。[来源：Google DeepMind Lyria 模型说明](https://deepmind.google/models/lyria/)

**为什么重要**

音乐模型开始从短演示片段进入可以编程调用的完整创作流程。结构、时长、人声语言和图片输入都可控制后，开发者能够把它接入视频配乐、游戏原型或品牌素材工作流。

可用范围扩大也不会自动解决版权和创作者权益问题。SynthID 提供的是识别 Google 生成内容的一种技术线索，不等于作品来源、训练许可或商业使用权已经被完整证明。使用者仍需查看服务条款，并人工检查歌词、相似性和项目授权要求。

### HyperPod InstantStart 为什么先限制操作，再让智能体接管流程？

**发生了什么**

北京时间 9 月 5 日 00:12，AWS 介绍开源项目 HyperPod InstantStart。它把 Amazon EKS 和 SageMaker HyperPod 的集群创建、容量设置、存储、训练、推理部署和节点操作集中到一个容器中，同时提供网页界面、REST 接口和模型上下文协议（Model Context Protocol，MCP）工具。[来源：AWS 技术说明](https://aws.amazon.com/blogs/machine-learning/run-agent-driven-amazon-sagemaker-hyperpod-operations-with-instantstart/)、[项目仓库](https://github.com/haozhx23/HyperPod-InstantStart)

项目为智能体提供 38 个领域工具，而不是直接交出完整 AWS 命令行权限。网页和智能体调用同一套后端接口，都会经过相同参数校验和状态记录；较长操作被拆成可重试阶段，智能体在可用区、实例和容量类型等决策上暂停等待用户选择。

AWS 同时写明了部署边界：Kubernetes 权限、网络出口和 IAM 身份仍由使用者负责，技能文件会影响容量、成本与可用性，应像后端代码一样审查。示例模板为了方便允许管理端口公开访问，正式使用前需要改为受限访问；这也说明该项目不是开箱即用的安全托管服务。

**为什么重要**

基础设施操作包含费用高、耗时长和难以撤销的步骤。把可执行动作限制为带业务含义的工具，再给每个动作配套状态查询和重试规则，比让智能体自由拼接云命令更容易检查和恢复。

这个方案的通用经验是，可靠性主要来自底层接口，而不是提示词。若网页与智能体共享同一套受限操作，参数校验、幂等处理和权限规则只需实现一次；智能体只是新的入口，不会绕开原有控制。

### Z1T 的百倍能效数字距离真实大模型还有多远？

**发生了什么**

Extropic 发布 Z1T，一组为 Z1 概率芯片设计的稀疏类 Transformer 模型。传统 GPU 擅长密集矩阵运算，Z1 的计算单元则只有固定、稀疏的物理连接；研究团队因此用动态双曲正切归一化、门控卷积注意力和稀疏投影改造模型结构，并让 FPGA 处理不适合 Z1 的部分。[来源：Extropic Z1T 技术说明](https://extropic.ai/writing/z1t/)

Extropic 开放了一次较大实验的模型权重和 JAX 训练方案。[来源：Z1T 模型资源](https://huggingface.co/Extropic-AI)、[稀疏模型训练仓库](https://github.com/extropic-ai/sparse-transformers)

页面标题强调相对 GPU 超过 100 倍的能效提升，但正文给出的范围更窄：11.55M 参数小模型在假设 H100 只有 10% 利用率时，排除最终词表输出和芯片间数据移动，估算每个词元的能耗约低 139 倍；H100 利用率提高到 50% 或 100% 时，差距降到约 28 倍或 14 倍。Z1 数字来自以早期芯片实验为锚点的理论估算，所需芯片数量没有建模，加入最终输出后 FPGA 会占据主要能耗。

**为什么重要**

AI 芯片与模型通常分别优化，Z1T 展示了另一条路线：接受硬件的稀疏连接约束，从训练阶段改变模型结构。即使当前模型能力有限，这种软硬件共同设计也可能为解码阶段提供不同于继续堆叠 GPU 的选择。

现阶段最重要的是不要把局部估算写成大模型已经在真实硬件上实现百倍节能。公开权重和训练方案便于外部检查模型侧结果，但完整结论还需要实际 Z1 系统、通信成本、最终输出层、批处理和更大模型的端到端测量。

## 值得关注

### AI 的下一轮竞争可能发生在运行时，而不只是在模型榜单

HydraFusion 根据任务选择模型和流程，Microsoft 用同一家族覆盖精细与高吞吐图像任务，AWS 则让网页和智能体共享受限接口。它们共同说明，真正交付结果的系统正在负责路由、复核、计费和失败恢复。单个模型的最高分仍有意义，但不足以描述一次实际工作的质量和成本。

### 可验证不等于易复现，更不等于易理解

费马大定理形式化通过证明核心检查，却需要庞大资源才能完整重建；Extropic 开放模型和训练方案，却仍缺少完整硬件上的端到端测量。公开产物只是验证的起点。读者还需要知道检查需要什么资源、哪些环节依赖厂商自报，以及自然语言说明是否准确对应机器检查的对象。

### 生成媒介越完整，来源与授权问题越难留到最后处理

Lyria 3.5 可以生成带歌词和人声的分钟级音乐，MAI-Image-2.6 能结合多张参考图与网页信息。输入来源、人物身份、作品相似性和输出授权因此会同时进入一次生成。水印和安全过滤可以提供线索，但产品团队仍需在素材进入模型前记录授权，并在成品发布前人工复核。
